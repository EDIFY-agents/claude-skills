How it works

Brief to verify, one graph underneath, every step a file.

Each step is written twice below: once in plain language, once in the mechanism. A filled square means EDIFY does it today. A hollow amber square means it works, degraded, and says so. A dashed square means it is not claimed.

01 / Think hard once

Spec, plan, tasks

The expensive thinking happens once, in writing, and ends at a human.

/spec turns a brief into a specification: what is being built, why, and the assertions that will later become tests. /plan records technology decisions with exact versions and the milestones the build must not re-make. /tasks reads the spec, the plan and the codebase graph and writes a phased task list anchored to real files and line ranges. All three use the strongest model you have, and all three stop for a person to read them.

Why. Most rework comes from decisions that were never written down, so every session made them again. Writing them once turns the rest of the work into following instructions.

02 / The map

The codebase graph

A map extracted from your code. Not invented by another model.

edify init reads every file and writes the graph to .edify/graph/: every file, module, exported symbol, route and table, with the edges between them, as sorted, checksummed text. Your agent shells out to edify graph to ask where something is defined, what depends on it, and whether two tasks touch the same files. A rebuild over unchanged source is byte-identical.

Why. Agents rarely fail from lack of intelligence. They fail from wrong, stale or missing context. A question answered from the map costs a line; re-exploring the repo costs the session.

03 / Then build without thinking

Build

Tests first. Then the cheapest model that follows instructions makes red go green.

Phase 2 of every /build turns each assertion in the spec into an executable test that fails, before any core logic exists. Contracts are frozen at the end of phase 1; everything after phase 2 is making those tests pass, phase by phase, in the order tasks.md sets, with an exit check at the end of each. Progress is a number anyone can watch instead of a claim anyone has to trust.

Why. A cheap builder is safe when it is hitting a target that already exists, not judging whether its own work is correct.

04 / Evidence

Verify

An independent pass that anyone can re-run, at any time.

/verify checks the code against the spec and the plan and writes verification.md. It runs on a strong model and never in a session that wrote code. Alongside it, edify check reports what is wrong with the documents themselves, with a file, a line, and a rule name.

Why. An implementer approving its own work is not verification. And "it works" is a claim; a report anyone can reproduce is evidence.

05 / The CLI

Six commands you will actually type.

The slash commands run inside your agent. These run in your terminal, work offline, and print plain text or --json.

edify initDetects the stack, extracts the graph, scrapes conventions, installs matching skills, writes a short CLAUDE.md, and records every file it put there.
edify doctorGreen, amber, red. Amber means something works, degraded, and names where.
edify graphwhere, dependents, defines, references, overlap. Answers carry a file and a line.
edify checkWhat is wrong with the documents. --fix, --json, --exit-code.
edify governanceEvery installed file with its origin, licence and hash, and whether it changed since.
edify feedbackWrites a file on your machine and prints the command you run to send it. Nothing leaves on its own.

07 / Limits, first

What EDIFY does not do.

It does not wrap the agent runtime, host a model, or route between providers.
It does not run a server, a daemon, or a database.
It does not enforce anything at runtime. Gates live in your CI, if you want them.
It does not make a weak model competent. It makes a competent model efficient.
It is not for a solo developer on a small project. The value starts where the codebase stops fitting in the context window.
